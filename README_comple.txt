# 모두의 아트 — 구현 현황 및 설계안

## 현재 구현 단계

현재 구현은 계획된 **3단계(전시 공간 CRUD·대표 이미지·마이페이지 통계)**까지 진행되었습니다.

- 회원가입·로그인·세션 및 접근 제어
- 작품 생성·조회·수정·삭제
- 펜·지우개·채우기·전체 지우기·스포이드 드로잉 도구
- 전시 공간 생성·조회·수정·삭제
- 사용자당 전시 공간 최대 5개 제한
- 전시 공간 이름·소개 입력 및 검증
- PNG/JPG 대표 이미지 업로드·교체·삭제
- 마이페이지의 전시 공간 수·작품 수 통계

아이소메트릭 블록 편집, 블록 디자인, 액자, 공개 관람, 좋아요, 방명록은
다음 단계에서 구현할 예정입니다.

README 전체(1~12장)를 읽고 분석한 문서입니다. 아래 설계안과 미결정 사항은
현재 구현 이후의 확장 작업을 위한 참고 자료입니다.

## 1. 요구사항 분석 및 기능 간 의존 관계

### 기능 단위와 선행 조건

| ID | 기능 | 선행 의존 |
|---|---|---|
| F1 | 회원가입·로그인·세션 | 없음 |
| F2 | 접근 제어(비로그인 → 로그인 이동, 소유자 검사) | F1 |
| F3 | 드로잉 툴(펜·지우개·채우기·전체 지우기) | 없음 (공통 모듈) |
| F4 | 작품 CRUD (512×512 PNG) | F1, F3 |
| F5 | 아이소메트릭 엔진(투영, 렌더링, 클릭 판정) | 없음 (공통 모듈) |
| F6 | 블록 디자인 CRUD·편집기(면 3개 × 32×32) | F1, F3, F5 |
| F7 | 전시 공간 CRUD·대표 이미지 (최대 5개) | F1 |
| F8 | 전시 공간 편집기 (a) 블록 설치/제거 (b) 디자인 적용/변경 (c) 액자 설치/제거/교체 | F5, F7 / F6 / F4 |
| F9 | 전시 공간 관람(공개) | F5, F7 |
| F10 | 전시 공간 목록·정렬 (main, gallery_list, gallery_user) | F7, F11(좋아요 수) |
| F11 | 좋아요 | F1, F7 |
| F12 | 방명록(작성·수정·삭제·페이징) | F1, F7 |
| F13 | 마이페이지 | F4, F7 |
| F14 | 연쇄 삭제·참조 무결성 규칙 | F4, F6, F7, F8 (횡단 관심사) |

```
F1 인증 ─┬─ F4 작품 ──────────────┐
         ├─ F6 블록 디자인 ─┐       ├─ F8c 액자
         ├─ F7 전시 공간 ───┼─ F8a 블록 설치/제거 ─ F8b 디자인 적용
         │                  ├─ F9 관람 ─┬─ F11 좋아요
         │                  │           └─ F12 방명록
         │                  └─ F10 목록/정렬 (좋아요 수 필요)
F3 드로잉 툴 ── F4, F6이 공유
F5 아이소 엔진 ── F6 미리보기 / F8 편집기 / F9 관람이 공유
```

### 설계에 영향을 주는 핵심 관찰

1. **공통 모듈이 두 개 있습니다.** 드로잉 툴(F3)은 작품과 블록 디자인이, 아이소메트릭 엔진(F5)은 디자인 미리보기·편집기·관람이 함께 씁니다. 이 둘을 먼저 독립 모듈로 만들면 재작업이 크게 줄어듭니다.
2. **참조 관계가 많아 삭제 규칙이 가장 위험합니다.** 디자인 삭제 → 블록은 회색으로, 작품 삭제 → 액자는 빈 액자로, 블록 삭제 → 액자 동반 삭제, 전시 공간 삭제 → 하위 전부 삭제입니다. 이 규칙은 데이터 설계 단계에서 확정해야 합니다.
3. **관람은 "다른 사용자의 데이터"를 읽습니다.** 방문자는 소유자의 디자인과 작품 이미지를 보게 되므로, "다른 사용자의 디자인은 사용할 수 없다"는 규칙은 **관리·선택에만** 적용되고 **렌더링용 읽기는 공개**여야 합니다. 이미지 접근 방식도 이 점을 전제로 설계해야 합니다.
4. **블록 개수는 사실상 최대 1,200개입니다.** 20×20×3 칸에 칸당 블록 1개라서 "개수 제한 없음"과 충돌하지는 않습니다. 렌더링 성능 걱정은 크지 않습니다.
5. **좋아요순 정렬은 전체 전시 공간의 좋아요 수가 필요합니다.** 파일 기반 저장에서는 목록 조회 성능이 설계 이슈가 되므로 3·4장에서 다룹니다.

## 3. JSON 데이터 구조와 관계

### 설계 원칙

- ID는 불투명한 값(`u_`, `g_`, `a_`, `d_`, `b_` + UUID)을 씁니다. 아이디(한글 포함)를 파일 경로에 쓰면 유니코드 정규화와 대소문자 문제가 생깁니다.
- 모든 JSON 파일 최상단에 `schemaVersion`을 둡니다.
- 시간은 ISO 문자열(UTC)로 저장합니다.
- 이미지는 JSON에 넣지 않고 파일로 저장하며, 경로는 ID 규칙으로 유도합니다. 파일 갱신 시 브라우저 캐시를 피하도록 `rev`(정수)를 올립니다.

### 파일별 스키마

```jsonc
// data/users.json
{ "schemaVersion": 1, "users": [
  { "id": "u_…", "username": "모두", "usernameKey": "모두",   // key = NFC + 소문자 (중복 판정용)
    "passwordHash": "…", "createdAt": "…" } ] }

// data/users/{userId}/artworks.json
{ "artworks": [
  { "id": "a_…", "title": "노을", "titleKey": "노을", "description": "",
    "createdAt": "…", "updatedAt": "…", "rev": 1 } ] }

// data/users/{userId}/designs.json
{ "designs": [
  { "id": "d_…", "name": "벽돌", "nameKey": "벽돌",
    "createdAt": "…", "updatedAt": "…", "rev": 1 } ] }   // 면 이미지는 파일 3개

// data/galleries/{galleryId}/gallery.json
{ "id": "g_…", "ownerId": "u_…", "name": "…", "description": "",
  "cover": null,                    // 또는 "g_….jpg"
  "createdAt": "…",
  "blocks": [
    { "id": "b_…", "x": 3, "y": 7, "z": 0,       // x,y: 0~19 / z: 0~2
      "designId": null,                           // null = 기본 회색
      "frame": null }                             // 또는 { "artworkId": "a_…" | null }
  ] }                                              // artworkId null = 빈 액자

// data/galleries/{galleryId}/likes.json
{ "userIds": ["u_…"] }

// data/galleries/{galleryId}/guestbook.json
{ "entries": [
  { "id": "m_…", "authorId": "u_…", "content": "…",
    "createdAt": "…", "updatedAt": "…" } ] }       // 화면에는 createdAt의 날짜만 표시
```

### 관계

```
User 1 ─ N Artwork        User 1 ─ N BlockDesign        User 1 ─ N Gallery (최대 5)
Gallery 1 ─ N Block (좌표 (x,y,z) 유일, 최대 1,200)
Block N ─ 0..1 BlockDesign   (designId, null = 회색)
Block 1 ─ 0..1 Frame         (블록에 내포)
Frame N ─ 0..1 Artwork       (artworkId, null = 빈 액자)
Gallery 1 ─ N GuestbookEntry (N ─ 1 User)
Gallery N ─ M User           (Like, 쌍 유일)
```

액자는 "블록 앞면당 1개"이고 블록과 생명주기가 같아서 블록 안에 내포했습니다. 작품과의 관계는 `artworkId` 참조로만 두어, 명세의 "작품 원본과 액자 연결을 분리" 요구를 충족합니다.

### 삭제 시 처리 규칙

| 삭제 대상 | 함께 삭제 | 값만 변경 | 유지 |
|---|---|---|---|
| 전시 공간 | 블록, 액자, 방명록, 좋아요, 대표 이미지 파일(제안) | 없음 | 작품, 블록 디자인 |
| 블록 | 그 블록의 액자 | 없음 | 작품 파일, 디자인 |
| 액자 | 없음 | 없음 | 블록, 작품 |
| 작품 | 작품 레코드 + PNG 파일 | 이 작품을 참조하는 액자의 `artworkId` → null | 블록, 액자 |
| 블록 디자인 | 레코드 + 면 이미지 3개 | 이 디자인을 쓰던 블록의 `designId` → null | 블록 위치, 액자 |

- 작품과 디자인은 소유자만 쓸 수 있으므로, 참조를 정리할 범위는 **그 소유자의 전시 공간(최대 5개)** 으로 한정됩니다.
- 서버는 읽을 때도 "끊어진 참조는 회색 블록·빈 액자로 취급"하는 방어 로직을 둡니다. 삭제 중 장애가 나도 화면이 깨지지 않게 하기 위해서입니다.

### 목록·정렬 성능

전시 공간이 폴더별로 흩어져 있어서 좋아요순 목록을 만들려면 전체를 읽어야 합니다. 서버 시작 시 전시 공간 요약(이름, 소유자, 좋아요 수, 생성일)을 **메모리 캐시**로 올리고, 변경 시 파일과 캐시를 함께 갱신하는 방식을 제안합니다. 서버가 단일 프로세스이고 세션도 메모리라는 전제와 맞습니다.

## 4. 서버와 클라이언트의 역할

| 영역 | 서버 | 클라이언트 |
|---|---|---|
| 인증 | 가입 검증, 해시, 세션 발급·파기, `/me` | 오류 문구 표시, 상단 메뉴 전환 |
| 접근 제어 | 페이지·API 가드(페이지는 302, API는 401/403), 소유자 검사 | 401 응답 시 로그인 페이지로 이동하는 공통 처리 |
| 검증 | **모든 규칙의 최종 판정**(길이, 중복, 한도, 좌표 범위, 소유권) | 입력 중 즉시 피드백(글자 수 카운터 등). 보조 수단 |
| 저장 | JSON·이미지 입출력, 원자적 쓰기, 동시성 제어, 연쇄 삭제 | 없음 |
| 이미지 | PNG/JPG 시그니처·크기 검사, 파일 교체·삭제 | 캔버스에서 PNG 생성·업로드 |
| 드로잉 | 없음 | 펜·지우개·채우기·전체 지우기, 편집 중 상태(저장 전에는 서버 반영 없음) |
| 아이소메트릭 | 없음 | 투영·렌더링·클릭 좌표 판정, 텍스처 캐시, 미리보기 |
| 편집기 | 각 조작의 유효성(점유 칸, 층 범위, 참조 소유권) 검증 후 반영 | 모드 상태, 확인 창, 선택 중인 디자인·작품 |
| 목록·정렬 | 정렬(좋아요순 동률은 최신순), 페이지 분할 | 정렬 UI, 렌더링 |
| 좋아요 | 중복 방지, 개수 집계 | 버튼 상태 표시 |
| 방명록 | 작성자 권한 검사, 10개 단위 페이징, 마지막 페이지 보정 | 인라인 수정 UI, 글자 수, 페이지 번호 구성, 스크롤 |

### API 윤곽 (경로명은 제안)

| 그룹 | 엔드포인트 |
|---|---|
| 인증 | `POST /api/auth/signup`, `login`, `logout` / `GET /api/auth/me` |
| 내 정보 | `GET /api/me` (아이디, 가입일, 전시 공간 수, 작품 수) |
| 작품 | `GET/POST /api/me/artworks`, `PATCH/DELETE /api/me/artworks/:id`, 이미지 교체 |
| 디자인 | `GET/POST /api/me/designs`, `PATCH/DELETE /api/me/designs/:id` |
| 전시 공간 | `GET /api/galleries?sort=&page=`, `GET /api/users/:username/galleries`, `GET /api/galleries/:id`(렌더링 묶음: 블록, 사용 디자인, 사용 작품, 좋아요 수, 내 좋아요 여부), `POST`, `PATCH`, `PUT cover`, `DELETE` |
| 블록·액자 | `POST …/blocks`, `PATCH …/blocks/:id`(디자인 변경), `DELETE …/blocks/:id`, `PUT …/blocks/:id/frame`(설치·교체), `DELETE …/frame` |
| 좋아요 | `PUT/DELETE …/like` (같은 요청을 반복해도 결과가 같게) |
| 방명록 | `GET …/guestbook?page=`, `POST`, `PATCH /:entryId`, `DELETE /:entryId` |

편집기 API는 갤러리 전체를 통째로 저장하는 방식이 아니라 **조작 단위**로 나눴습니다. 서버가 규칙을 조작마다 검증할 수 있고, 두 탭에서 편집해도 덮어쓰기 사고가 적습니다.

## 5. 구현 순서

| 단계 | 내용 | 완료 확인 기준 |
|---|---|---|
| 0 | 미결정 사항 확정, 골격(Express, 세션, 설정 상수), 파일 저장소(원자적 쓰기, 뮤텍스), ID·문자열 유틸, 오류 응답 형식 | 서버 기동, 저장소 읽기·쓰기 동작 |
| 1 | 인증(가입·로그인·로그아웃·`/me`), 접근 가드, 상단 메뉴, `sign_in`, `main` 뼈대 | 모든 가입·로그인 오류 문구, 리다이렉트 규칙 |
| 2 | **드로잉 툴 모듈** + 작품 CRUD + `item_create` + `item_manage` | 생성·수정(이어 그리기)·삭제, 제목 중복 검사 |
| 3 | 전시 공간 CRUD + 대표 이미지 + `gallery_create` + 마이페이지(전시 공간·작품 관리, 통계) | 5개 한도, 이미지 검증, 삭제 확인 |
| 4 | **아이소메트릭 엔진** + `gallery_edit`(회색 블록만): 층 이동, 설치·제거 모드, 클릭 판정 | 20×20×3 전 칸 설치·제거, 점유 칸 무반응 |
| 5 | 블록 디자인 CRUD + `design_edit`(면별 캔버스, 면 매핑, 저장 시 미리보기 갱신) + 편집기에 디자인 선택·변경 + 디자인 삭제 연쇄 | 수정 시 사용 중인 모든 블록 반영, 삭제 시 회색 전환 |
| 6 | 액자 설치·제거·작품 교체, 빈 액자, 작품 삭제 연쇄 | 작품 삭제 후 빈 액자 유지, 블록 제거 시 액자 동반 제거 |
| 7 | `gallery_view`(관람 전용), 전시 공간 목록·정렬(`main`, `gallery_list`, `gallery_user`) | 3종 정렬, 좋아요 동률 처리 |
| 8 | 좋아요 + 방명록(작성·인라인 수정·삭제·페이징·마지막 페이지 보정) | 비로그인 리다이렉트, 페이징 경계 케이스 |
| 9 | 전시 공간 삭제 연쇄, 오류 처리 점검, 고아 파일 정리, 반응형, 전체 시나리오 점검 | 명세 체크리스트 전 항목 통과 |

4단계(엔진)는 이 프로젝트에서 가장 위험한 부분이라, 디자인이나 액자 없이 회색 블록만으로 먼저 검증하도록 순서를 잡았습니다. 5·6단계는 그 위에 얹는 구조입니다.

## 6. 미결정 사항 및 충돌 가능성

### A. 구현 전에 꼭 결정해야 할 사항

1. **3D 위치를 2D 클릭으로 지정하는 방식.** 아이소메트릭 화면에서는 한 번의 클릭이 여러 칸(x,y,z)에 대응할 수 있습니다. 공중 설치를 허용하면 "면을 클릭해 옆에 붙이는" 방식으로는 해결되지 않습니다. **제안:** "현재 편집 층" 선택기를 추가하고, 클릭을 그 층의 바닥면으로 환산합니다. 다른 층은 흐리게 표시합니다. 명세에 없는 UI 요소라 승인이 필요합니다.
2. **"앞면"의 방향과 가려진 면 처리.** 아이소메트릭에서 세로 면은 두 개(좌·우)인데 명세는 앞면·옆면 둘로 나눕니다. 어느 쪽이 앞면인지 정해야 합니다. 또 다른 블록에 가려진 앞면에는 액자를 설치할 수 있는지, 액자가 있는 블록 앞에 나중에 블록을 놓으면 어떻게 되는지도 정해야 합니다. **제안:** 보이는 면만 설치·클릭 가능하게 하고, 가려진 액자는 허용하되 그대로 둡니다.
3. **편집기의 모드 체계.** 명세에 나온 동작은 일반, 블록 설치, 블록 제거, 액자 설치, 액자 제거까지입니다. "설치된 블록의 디자인 변경"과 "액자 작품 교체"는 어느 모드에서 하는지 없습니다. 액자 설치 모드에서 기존 액자를 클릭하면 교체인지 무반응인지도 불분명합니다. **제안:** "디자인 변경" 모드를 추가하고, 액자 교체는 액자 설치 모드에서 작품을 선택한 채 기존 액자를 클릭하는 동작으로 합니다.
4. **편집기 저장 방식.** 디자인과 작품은 "저장 버튼"이 있지만 블록·액자 편집에는 저장 개념이 없습니다. **제안:** 조작마다 즉시 서버에 저장합니다.
5. **화면 구성.** 2장의 추가 페이지 5개를 승인해야 합니다. `gallery_user`와 디자인 관리 페이지의 진입 경로도 정해야 합니다. 디자인 관리는 마이페이지에 포함하지 않는다는 규정이 있으므로, **제안:** `gallery_edit` 안의 "디자인 관리" 버튼을 진입점으로 합니다. `gallery_user`는 소유자 아이디를 클릭해 진입합니다.
6. **드로잉 툴 사양.** 색 선택, 펜 굵기, 지우개 결과(투명인지 흰색인지), 전체 지우기 후 배경색, 되돌리기 여부가 명세에 없습니다. 작품(512px 자유 그리기)과 블록 면(32×32 도트)이 같은 툴을 쓰는 점도 영향을 줍니다. **제안:** 색 선택과 굵기를 제공하고, 지우개와 전체 지우기는 투명 처리하며, 되돌리기는 1차 범위에서 제외합니다.
7. **데이터 저장 구조 승인.** (a) 블록 디자인의 면 이미지를 별도 PNG 파일로 저장할지(제안), JSON에 인라인으로 넣을지. (b) "사용자별 분리 저장"을, 작품·디자인은 사용자 폴더에, 전시 공간은 ID 폴더(`ownerId` 포함)에 두는 방식으로 해석해도 되는지. (c) 3장의 메모리 캐시 사용 여부.
8. **프론트엔드 스택과 허용 패키지.** 프레임워크 언급이 없습니다. **제안:** 바닐라 JS(ES 모듈)와 Canvas 2D를 씁니다. 서버 쪽은 비밀번호 해시와 파일 업로드 처리를 위해 `express`, `express-session` 외에 몇 개의 패키지가 필요하니 허용 범위를 확인받고 싶습니다.
9. **비밀번호 해시 방식과 최대 길이.** 명세는 "4자 이상"만 정하고 상한이 없습니다. bcrypt는 72바이트 초과분을 무시합니다. **제안:** Node 내장 `scrypt`를 쓰거나, bcrypt를 쓴다면 상한을 둡니다.
10. **전시 공간 이름 규칙.** 최대 길이, 중복 허용 여부, 공백만 입력한 경우가 정해지지 않았습니다. **제안:** 최대 20자, 중복 허용, 앞뒤 공백 제거 후 필수 검사.
11. **작품 이미지 "용량 제한 없음"의 현실적 처리.** 서버에는 요청 본문 한도가 있고 무제한은 서버 장애로 이어질 수 있습니다. 512×512 PNG는 크기가 자연히 작으므로, **제안:** 규격(PNG, 512×512)을 검증하고 넉넉한 기술적 상한(예: 5MB)을 사용자에게 보이지 않게 둡니다.
12. **참조 정리 방식과 파일 정리.** 3장의 "즉시 연쇄 정리 + 읽을 때 방어" 이중 방식을 제안합니다. 전시 공간 삭제 시 **대표 이미지 파일도 삭제할지**는 명세에 없어서 확인이 필요합니다(제안: 삭제).
13. **목록 페이지 분할.** `main`, `gallery_list`, `gallery_user`와 작품·디자인 목록에 페이지 분할이나 표시 개수 제한이 정해지지 않았습니다. `main`의 "공개 전시 공간 목록"이 어떤 기준(전체, 최신 N개 등)인지도 불명확합니다.

### B. 명세 내부의 충돌·불일치

1. **10장·12장의 "미결정" 목록에 이미 결정된 항목이 남아 있습니다.** "비로그인 방명록 작성 처리"는 3-1장과 11장에서 로그인 이동으로 확정됐습니다. "방명록 등록 후 새로고침 여부"는 마지막 절에서 "작성창을 닫고 현재 페이지 유지"로 일부 확정됐는데, **새 글이 목록에 언제 보이는지**(1페이지를 보던 중이면 즉시 추가되는지)는 아직 비어 있습니다.
2. **마이페이지와 작품 관리 페이지의 역할이 겹칩니다.** 3-1장은 마이페이지에서 작품을 수정·삭제한다고 하고, 같은 장에서 작품 관리 페이지가 "내 작품 관리" 링크로 열린다고 합니다. **제안:** 마이페이지에는 작품 수와 링크만 두고, 수정·삭제는 작품 관리 페이지에서 합니다.
3. **방명록의 "전체 새로고침"과 "현재 페이지 유지"가 맞물립니다.** 수정·삭제 후 전체 새로고침을 하면 보던 페이지 번호가 사라질 수 있습니다. **제안:** 페이지 번호를 URL 쿼리(`?page=`)로 유지합니다.
4. **"카메라 확대·축소 불가, 20×20 전체 표시"와 작은 화면.** 고정 크기로 그리면 모바일에서 잘립니다. 화면 폭에 맞춘 **비율 축소(fit-to-screen)** 가 "확대·축소 미지원"에 해당하지 않는다고 해석해도 되는지 확인이 필요합니다.
5. **블록 디자인 신규 생성 시 미리보기 상태.** "저장 시에만 미리보기 갱신" 규칙에서는 첫 저장 전에 미리보기에 무엇을 보여줄지 정해야 합니다. **제안:** 회색 블록 또는 빈 블록.
6. **빈 액자 문구와 액자 외형.** 액자는 블록 앞면의 80% 크기이고 아이소메트릭에서는 기울어진 작은 영역이 됩니다. 이 안에 "빈 액자"를 읽을 수 있게 그리는 방법(글자 크기, 기울임)과 액자 테두리의 시각 사양(색, 두께, 80%에 포함되는지)이 없습니다.
7. **용어 혼용.** "작품 삭제"와 "작품 원본 파일 삭제"가 섞여 쓰입니다(예: 254행). 같은 동작(레코드와 PNG를 함께 삭제)으로 통일해 해석하겠습니다.
8. **같은 작품을 여러 액자·여러 전시 공간에 쓸 수 있는지**에 대한 언급이 없습니다. 제한이 없는 것으로 가정합니다.
9. **좋아요 소유자 허용과 좋아요순 정렬.** 소유자도 좋아요를 누를 수 있어서 정렬을 스스로 끌어올릴 수 있습니다. 의도라면 그대로 가고, 아니라면 알려주세요.
10. **"로그인 후 항상 메인 이동."** 좋아요나 방명록을 누르려다 로그인하면 원래 자리로 돌아오지 못합니다. 명시된 결정이라 따르되, 사용성에 영향이 있다는 점만 기록합니다.

### C. 이견이 없으면 제가 정해서 진행할 세부 사항

- **아이디 규칙:** 한글은 완성형(가~힣)만 허용하고 자모는 불가. 중복은 대소문자를 무시하고 유니코드 정규화(NFC) 기준으로 판정하되 표시는 입력한 그대로.
- **글자 수:** 코드포인트 기준으로 서버와 클라이언트가 동일하게 계산하고, 앞뒤 공백은 제거한 뒤 검사. 붙여넣기로 100자를 넘기면 100자에서 자름.
- **중복 검사(작품 제목, 디자인 이름):** 앞뒤 공백 제거 후 대소문자 무시.
- **날짜 표시:** 한국 시간 기준 `YYYY-MM-DD`. 저장은 UTC ISO.
- **아이디 중복 문구:** "이미 사용 중인 아이디입니다."
- **방명록 페이지 번호:** 현재 ±2개와 첫·마지막 페이지를 표시하고 나머지는 `...`.
- **세션 쿠키:** 만료 시간을 두지 않아 브라우저를 닫으면 사라짐. `httpOnly`, `sameSite=lax`를 쓰고, 로그인 시 세션 ID를 새로 발급.
- **오류 응답:** 필드 오류는 `{error:{code,message,field}}`. 비소유자 접근은 403, 없는 리소스는 안내 페이지.
- **파일 저장 안전성:** 임시 파일에 쓴 뒤 이름 변경(원자적), 파일별 직렬화. 여러 파일에 걸친 작업은 "새 데이터 기록 → 참조 갱신 → 옛 파일 삭제" 순서로 처리. 시작 시 고아 파일 정리는 선택 사항.
- **이미지 접근:** `/uploads`를 정적으로 공개. UUID 파일명이라 추측이 어렵습니다. 소유자·참조 여부로 접근을 제한하는 방식은 복잡도가 커서 제외했습니다.
- **이미지 캐시:** `?v=rev`로 갱신 반영.

승인하시기 전에 **A의 1~13번**에 대한 의견을 주시면 가장 도움이 됩니다. 특히 A1(층 선택기)과 A3(모드 체계)은 편집기 전체 설계를 좌우합니다. 위 제안이 괜찮으면 "A는 제안대로"라고만 답해 주셔도 됩니다. 승인 전까지 코드는 작성하지 않겠습니다.
