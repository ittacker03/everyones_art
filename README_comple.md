1. 프로젝트 개요

프로젝트명은 모두의 아트 (Everyone’s Art)다. 사용자가 작품과 블록을
이용해 전시 공간을 꾸미고 공유하는 웹 서비스다.

기술 방향은 Node.js/Express, HTML/CSS/Vanilla JavaScript, JSON 및 텍스트
파일 기반 데이터 저장, 별도 이미지 파일 저장, express-session 기반
로그인 상태 관리다. 현재 코드 구조를 먼저 파악하고 기존 구현을 존중한다.

2. 단계별 구현 현황

1단계 — 사용자 인증

상태: 완료

-   회원가입 및 로그인 등 인증 기능
-   세션 기반 로그인 상태 관리
-   인증이 필요한 페이지 및 기능 보호

세부 구현은 현재 소스 코드를 기준으로 유지한다.

2단계 — 작품 관리

상태: 완료

-   작품 생성 및 관리 기능
-   작품 드로잉/이미지 관련 기능
-   작품 데이터의 저장 및 조회

세부 구현은 현재 소스 코드를 기준으로 유지한다.

3단계 — 전시 공간 관리

상태: 완료

-   전시 공간 생성·조회·수정·삭제(CRUD)
-   사용자당 전시 공간 최대 5개 제한
-   대표 이미지 PNG/JPG 업로드·교체·삭제
-   마이페이지에 전시 공간 및 작품 통계 표시
-   사용자별 전시 공간 데이터 저장
-   3단계 구현 현황 문서화

주의: 1~3단계는 완료된 기능이다. 4단계 구현 과정에서 기존 기능을 임의로
재작성하거나 회귀시키지 않는다.

4단계 — 아이소메트릭 전시 공간 편집기

상태: 완료

목표는 사용자가 독립된 편집 화면에서 아이소메트릭 전시 공간을 보고,
키보드로 블록 설치·제거 위치를 선택해 편집할 수 있도록 하는 것이다.

독립 편집 페이지, 키보드 기반 선택 이동, 블록·액자 미저장 편집 및 저장,
페이지 이탈 보호까지 구현했다. 블록 디자인 CRUD는 다음 단계에서 진행한다.

3. 4단계의 페이지 구성 요구사항

3.1 편집기는 별도 HTML 페이지

-   전시 공간 꾸미기는 index.html에서 진행하지 않는다.
-   편집 전용 페이지인 gallery_edit을 별도의 HTML 페이지로 제공한다.
-   index.html에 편집기 화면을 삽입하거나, 메인 페이지의 일부 영역을
    편집기로 전용하지 않는다.
-   편집 화면은 넓은 작업 영역을 확보할 수 있도록 독립된 화면으로
    구성한다.
-   해당 페이지는 로그인 및 소유권 확인 등 기존 접근 제어 규칙을 따른다.
-   기존 Express 라우팅 및 views/ 구조를 먼저 조사하고, 프로젝트의 기존
    규칙에 맞춰 페이지를 추가한다.

3.2 편집기 기본 표시

기존 프로젝트의 전시 공간 규칙을 유지한다.

-   바닥 격자: 20 × 20
-   층: 총 3층
-   블록 크기: 1 × 1 × 1
-   투영 방식: 아이소메트릭
-   카메라: 고정
-   카메라 이동·확대·축소·회전: 제공하지 않음
-   바닥 타일 자체는 설치·삭제할 수 없음
-   공중 위치 설치 허용
-   전체 블록 수에 별도 총량 제한 없음

20 × 20 전체 바닥이 작업 화면에서 확인 가능하도록 한다. 실제 렌더링
크기와 반응형 처리 방식은 현재 화면 구조를 확인한 뒤 정하되, 사용자
조작을 위해 작업 영역을 불필요하게 작게 만들지 않는다.

4. 4단계 확정 조작 명세 — 최신 사용자 결정

4.1 편집 페이지와 기본 표시

- 편집기는 `index.html`과 분리된 `gallery_edit` 독립 HTML 페이지로 제공한다.
- 기존 Express 라우팅, `views/` 구조, 로그인 및 소유권 접근 제어를 따른다.
- 바닥 격자는 20×20, 층은 3개, 블록 크기는 1×1×1이다. 아이소메트릭 투영과 고정 카메라를 사용하고 카메라 이동·확대·축소·회전은 지원하지 않는다.
- 바닥 타일은 설치·삭제할 수 없다. 공중 설치를 허용하며 전체 블록 수에 별도 제한을 두지 않는다.
- 바닥 전체를 작업 화면에서 확인할 수 있게 한다. 화면 크기에 맞춘 실제 렌더링과 축소 방식은 구현 전 기존 화면 구조를 확인한다.

4.2 모드, 방향키 및 선택 위치

- 편집 화면에 `블록 설치`, `블록 제거`, `액자 설치`, `액자 제거` 버튼을 각각 둔다. 현재 활성 모드를 명확히 표시한다.
- 네 모드 모두 작업 확정 키는 `Enter`다. 현재 모드에 따라 실행되는 작업이 달라진다.
- 방향키는 월드 좌표축이 아니라 아이소메트릭 화면에 보이는 방향으로 인접한 한 칸씩 이동한다.

  키   화면상 이동 방향
  ---- ------------------
  ↑    왼쪽 위
  →    오른쪽 위
  ↓    오른쪽 아래
  ←    왼쪽 아래

- 선택 위치는 20×20 격자 범위 안에 둔다. 가장자리에서 바깥 방향으로 이동을 시도하면 멈추며 반대편으로 순환하지 않는다.
- 편집기를 처음 열면 중앙 네 칸 중 화면 기준 왼쪽 위 칸을 선택한다.
- 층 선택기는 `1층`, `2층`, `3층`으로 제공한다. 층 변경 시 `(x, y)`를 유지하고 `z`만 바꾼다. 선택 층의 같은 위치가 점유되어 있어도 선택 위치를 자동으로 옮기지 않으며, 해당 위치에는 설치할 수 없다.
- 층 변경, 모드 변경, 액자 제거 뒤에도 선택 좌표를 유지한다.
- 선택 위치는 테두리 또는 반투명 오버레이로 표시한다. 다른 블록에 가려져도 보이도록 블록 그래픽보다 위에 표시한다. 블록 설치·제거 모드는 다른 시각 스타일로 구분한다.
- 편집 조작 중 방향키가 페이지를 스크롤하지 않도록 한다. 텍스트 입력 요소에 포커스가 있으면 방향키 입력을 가로채지 않는다.
- 설치 위치나 제거 대상을 마우스 클릭으로 지정하지 않는다. 마우스는 디자인·작품 목록에서 항목을 선택할 때 사용한다.

4.3 블록 디자인 선택 및 블록 작업

- 편집 화면 한쪽에 현재 사용자가 만든 디자인 목록을 표시하고 마우스로 선택할 수 있게 한다. 다른 사용자의 디자인은 목록에 넣지 않는다.
- 목록에 `기본 회색` 항목을 제공한다. 디자인을 선택하지 않았거나 기본 회색을 선택하면 새 블록은 회색으로 설치한다.
- 선택한 디자인은 이후 새로 설치하는 블록에만 적용한다. 편집기에서 디자인을 선택하는 것만으로 이미 설치된 블록을 변경하지 않는다.
- 디자인 자체를 편집해 저장하는 경우에는 디자인 ID를 참조하는 기존 블록에 변경 내용이 반영되는 기존 요구를 유지한다. 이는 새 블록용 디자인을 선택하는 동작과 별개다.
- 설치 모드에서 빈 위치를 선택하고 `Enter`를 누르면 블록을 설치한다. 점유된 위치에는 설치하지 않는다. 설치 후 선택 좌표는 유지한다.
- 제거 모드에서 `Enter`를 누르면 해당 위치의 블록을 제거한다. 빈 위치에서는 제거하지 않는다.
- 블록 제거 시 부착된 액자도 함께 제거하지만 작품 파일·정보는 삭제하지 않는다.

4.4 액자 및 작품 작업

- 편집 화면 한쪽에 현재 사용자의 작품 목록을 표시하고 마우스로 작품을 선택하게 한다.
- 작품을 선택하고 액자 설치 모드에서 방향키로 위치를 선택한 뒤 `Enter`를 누르면 설치한다. 액자는 블록 앞면에만 설치한다.
- 블록 앞면에 이미 액자가 있으면 추가 설치를 막는다. 기존 액자를 먼저 제거해야 한다.
- 액자 설치 성공 후 액자 설치 모드를 종료하고 선택 작품을 해제한다.
- 액자 제거 모드에서 `Enter`를 누르면 액자와 작품 참조만 해제한다. 작품 원본 파일과 정보는 유지한다. 액자 제거 뒤에도 선택 좌표를 유지한다.
- 액자가 없는 위치에서 액자 제거를 확정하면 `제거할 액자가 없습니다`를 표시한다.
- 작품 자체를 작품 관리에서 삭제하면 작품 데이터와 이미지 파일은 삭제하되, 해당 액자는 빈 액자로 남긴다. 액자 제거와 작품 삭제는 별개 동작이다.
- 액자를 제거하지 않고 작품을 바로 교체하는 기능은 제공하지 않는다.

4.5 저장 및 페이지 이탈

- 블록·액자 편집 변경은 저장 버튼을 눌렀을 때 저장한다. 각 조작 직후 자동 저장하지 않는다.
- 저장 중에는 저장 버튼을 비활성화한다. 저장 성공 시 `저장 완료`를 3초간 표시한 뒤 숨긴다.
- 저장 실패 시 오류 안내와 `다시 저장` 버튼을 표시하고 편집 변경 내용을 유지한다.
- 저장 실패 후 사용자가 방향키로 선택 위치를 움직여 편집을 다시 시작하면 오류 안내와 재시도 버튼을 숨긴다. 미저장 변경 내용은 유지하고 일반 저장 버튼을 계속 사용할 수 있게 한다.
- 미저장 변경 사항이 있을 때 페이지를 나가려 하면 `저장하고 나가기`, `저장하지 않고 나가기`, `계속 편집`을 제공하며 기본 선택은 `계속 편집`이다.

5. 데이터 및 기존 구조와의 연계

이전 설계에서 제안된 블록 데이터 형태는 다음과 같다.

    {
      "id": "block-id",
      "x": 0,
      "y": 0,
      "z": 0,
      "designId": null,
      "frame": null
    }

-   x, y는 20 × 20 바닥의 좌표 범위를 나타낸다.
-   z는 최대 3개 층을 나타낸다.
-   designId는 적용된 블록 디자인을 나타낸다.
-   frame은 블록 앞면에 설치된 액자 정보를 나타내는 기존 설계 필드다.

중요: 위 구조는 이전 문서에서 제안된 예시다. 실제 구현의 저장 구조와
일치하는지 먼저 소스 코드를 확인한다. 이미 구현된 데이터 형식이 있다면
그 형식을 우선하고, 사용자 승인 없이 데이터 스키마를 교체하지 않는다.

이전 설계에는 블록 생성/수정/삭제 API를 개별 작업 단위로 호출하는 방안이
포함되어 있었다. 실제 API 경로와 저장 시점은 현재 코드 확인 후 결정한다.
프런트엔드에서 전체 전시 공간 데이터를 무조건 덮어쓰는 방식으로 새로
구현하지 않는다.

6. 구현 기술 관련 기존 제안

이전 설계에서 다음과 같은 프런트엔드 구조가 제안되었다.

-   Vanilla JavaScript 및 ES modules
-   Canvas 2D 렌더링
-   아이소메트릭 좌표 변환 모듈
-   렌더러
-   선택 위치 판정/이동 모듈
-   이미지/텍스처 캐시

이는 구현 후보이며, 사용자의 현재 코드와 라이브러리 구성을 조사한 뒤
적용한다. 기존 코드에 이미 적절한 렌더링 구조가 있다면 중복 구현하지
않는다.

7. 4단계 완료 기준

아래 기준을 모두 실제로 확인해야 4단계를 완료로 판단한다.

- ☐ 편집기는 `index.html`과 분리된 독립 페이지에서 동작한다.
- ☐ 20×20 아이소메트릭 바닥, 고정 카메라, 1~3층 선택이 제공된다.
- ☐ 층 변경 시 `(x, y)`가 유지되고 `z`만 변경된다.
- ☐ 방향키가 화면 기준으로 한 칸씩 이동하고 경계에서는 멈춘다.
- ☐ 최초 선택 위치는 중앙 네 칸 중 화면 기준 왼쪽 위다.
- ☐ 모드/층 변경 및 액자 제거 후 선택 좌표가 유지된다.
- ☐ 선택 표시가 블록에 가려지지 않고 설치·제거 모드가 구분된다.
- ☐ 네 모드가 각각 제공되며 모두 `Enter`로 확정한다.
- ☐ 점유 위치에는 블록을 설치하지 않고, 빈 위치에서는 제거하지 않는다.
- ☐ 블록 제거 시 액자는 함께 제거되고 작품 원본은 유지된다.
- ☐ 디자인 목록은 본인 디자인만 표시하고 `기본 회색` 선택이 가능하다.
- ☐ 선택 디자인은 새 블록에만 적용되며 기존 블록은 선택만으로 바뀌지 않는다.
- ☐ 작품 목록은 본인 작품만 표시하고 액자 설치 성공 후 모드와 작품 선택이 해제된다.
- ☐ 액자 중복 설치가 막히고 액자 제거는 작품 원본을 보존한다.
- ☐ 액자 없는 위치에서 제거를 확정하면 안내가 표시된다.

- ☐ 1~3단계의 기존 기능에 회귀가 없다.

## 11. 사용자와 문답으로 확정한 편집기 명세 — 최신 기준

이 절은 outputs 폴더의 `README_comple_decisions_01.md`부터 `README_comple_decisions_08.md`까지의 결정과 그 뒤 이어진 사용자 확인을 합친 최종 기준이다. 원본 본문이나 이전 결정 파일의 미정 목록과 다르면 이 절의 확정 내용을 우선한다.

### 11.1 모드와 키 조작

- 편집 화면에 `블록 설치`, `블록 제거`, `액자 설치`, `액자 제거` 버튼을 각각 둔다.
- 네 모드 모두 작업 확정에 `Enter`를 사용한다. 현재 활성 모드에 따라 설치 또는 제거 동작이 달라진다.
- 방향키는 아이소메트릭 화면에서 보이는 방향으로 한 칸씩 이동한다.

  키    화면상 이동 방향
  ----- ------------------
  `↑`   왼쪽 위
  `→`   오른쪽 위
  `↓`   오른쪽 아래
  `←`   왼쪽 아래

- 격자 가장자리에서 바깥 방향을 누르면 선택 위치가 멈춘다. 반대편으로 순환하지 않는다.
- 편집기 최초 진입 시 선택 위치는 20×20 바닥의 중앙 네 칸 중 화면 기준 왼쪽 위 칸이다.
- 층을 바꾸면 `(x, y)`를 유지하고 `z`만 변경한다. 모드 전환, 층 전환, 액자 제거 후에도 현재 선택 위치를 유지한다.
- 편집 조작 중 방향키가 페이지를 스크롤하지 않게 한다. 텍스트 입력 요소에 포커스가 있으면 방향키를 가로채지 않는다.
- 설치/제거 모드를 화면에서 명확히 구분하고, 선택 위치는 테두리 또는 반투명 오버레이로 표시한다. 선택 위치 표시는 다른 블록에 가려져도 보이도록 블록보다 위에 그린다.

### 11.2 블록 디자인과 설치·제거

- 편집 화면 한쪽에 현재 사용자가 만든 디자인만 목록으로 표시하고 마우스로 선택하게 한다. 다른 사용자의 디자인은 목록에 넣지 않는다.
- 목록에 `기본 회색` 선택지를 둔다. 디자인을 선택하지 않았거나 기본 회색을 선택하면 다음에 설치하는 블록은 회색이다.
- 선택한 디자인은 앞으로 새로 설치하는 블록에만 적용한다. 디자인을 선택하는 행위만으로 이미 설치된 블록은 바꾸지 않는다.
- 설치 모드에서 선택 위치에 블록이 없으면 `Enter`로 설치한다. 이미 블록이 점유한 위치에는 설치하지 않는다. 설치 후 선택 위치는 유지한다.
- 제거 모드에서 `Enter`를 누르면 해당 위치의 블록을 제거한다. 빈 위치에서는 아무 블록도 제거하지 않는다.
- 블록 제거 시 부착된 액자도 함께 제거하지만 작품 파일과 작품 정보는 삭제하지 않는다.
- 디자인 자체를 편집해 저장하는 동작은 디자인 ID를 참조하는 기존 블록에 적용하는 기존 요구를 유지한다. 이는 편집 화면에서 새 블록용 디자인을 고르는 동작과 별개다.

### 11.3 액자 설치·제거와 작품 보존

- 편집 화면 한쪽에 현재 사용자의 작품 목록을 표시하고 마우스로 액자에 사용할 작품을 고르게 한다.
- 작품을 선택한 뒤 액자 설치 모드에서 방향키로 위치를 선택하고 `Enter`를 누른다. 액자는 블록 앞면에만 설치한다.
- 이미 액자가 있는 블록에는 새 액자를 설치하지 않는다. 먼저 액자 제거 모드에서 기존 액자를 제거해야 한다.
- 액자 설치에 성공하면 액자 설치 모드를 종료하고 선택 작품도 해제한다.
- 액자 제거 모드에서 위치를 선택하고 `Enter`를 누르면 액자와 작품 참조만 제거한다. 작품 원본 파일과 작품 정보는 유지한다.
- 액자가 없는 블록 위치에서 액자 제거를 확정하면 `제거할 액자가 없습니다`를 표시한다.
- 액자 제거 뒤에도 선택 위치를 유지한다. 제거된 액자에 연결되어 있던 작품은 사용자 작품 목록에 남는다.
- 작품 자체를 작품 관리에서 삭제하는 경우는 별도 동작이다. 기존 README 규칙대로 작품을 삭제하면 연결된 액자는 빈 액자로 남는다.
- 액자 설치/제거 모드는 블록 설치/제거 모드와 별도 버튼으로 제공한다.

### 11.4 저장과 페이지 이탈

- 블록·액자 편집 변경은 저장 버튼을 눌렀을 때 저장한다. 설치·제거 직후 자동 저장하지 않는다.
- 저장 중에는 저장 버튼을 비활성화한다. 저장 성공 시 `저장 완료`를 3초간 표시한 뒤 자동으로 숨긴다.
- 저장 실패 시 오류 안내와 `다시 저장` 버튼을 표시하고 편집 변경 내용을 유지한다.
- 사용자가 방향키로 선택 위치를 움직여 편집을 다시 시작하면 오류 안내와 `다시 저장` 버튼을 숨긴다. 저장되지 않은 변경 내용은 그대로 유지하고 일반 저장 버튼은 계속 사용할 수 있게 한다.
- 저장되지 않은 변경 사항이 있을 때 페이지를 나가려 하면 `저장하고 나가기`, `저장하지 않고 나가기`, `계속 편집`을 제시한다. 기본 선택은 `계속 편집`이다.

### 11.5 완료 확인에 추가할 항목

- 네 편집 모드, 공통 `Enter`, 방향키 이동, 경계 정지, 최초 중앙 왼쪽 위 칸 및 선택 좌표 유지
- 디자인/작품 목록의 본인 소유 범위, 기본 회색 선택, 새 블록에만 디자인 적용
- 이미 액자가 있는 블록에 대한 설치 차단, 액자 제거 시 작품 보존, 액자 없음 안내
- 겹친 블록 위의 선택 표시
- 저장 버튼 동작, 저장 중 비활성화, 성공 후 3초 표시, 실패 후 재시도 및 변경 유지
- 미저장 변경 이탈 확인창의 세 선택지와 `계속 편집` 기본값

### 11.6 남아 있는 미결정 사항

- 아이소메트릭에서 어떤 세로 면을 액자의 `앞면`으로 볼지, 다른 블록에 가려진 면에 액자를 설치할 수 있는지
- 작은 화면에서 고정 카메라와 20×20 전체 표시를 함께 만족시키는 구체적인 반응형 축소 방식
- 기존 소스 코드와 맞는 실제 JSON 파일 구조, API 경로 및 블록·액자 저장 단위
- 저장 실패 후 서버가 부분 반영했는지 확인하고 복구하는 방식
- `저장하고 나가기`를 선택했을 때 저장 실패가 나면 페이지 이탈을 막고 어떤 안내를 할지
- 블록 디자인 관리 페이지로 진입하는 구체적인 경로
- 세부 UI 색상·간격 등 시각 표현

### 설계에 영향을 주는 핵심 관찰

1. **공통 모듈이 두 개 있습니다.** 드로잉 툴(F3)은 작품과 블록 디자인이, 아이소메트릭 엔진(F5)은 디자인 미리보기·편집기·관람이 함께 씁니다. 이 둘을 먼저 독립 모듈로 만들면 재작업이 크게 줄어듭니다.
2. **참조 관계가 많아 삭제 규칙이 가장 위험합니다.** 디자인 삭제 → 블록은 회색으로, 작품 삭제 → 액자는 빈 액자로, 블록 삭제 → 액자 동반 삭제, 전시 공간 삭제 → 하위 전부 삭제입니다. 이 규칙은 데이터 설계 단계에서 확정해야 합니다.
3. **관람은 "다른 사용자의 데이터"를 읽습니다.** 방문자는 소유자의 디자인과 작품 이미지를 보게 되므로, "다른 사용자의 디자인은 사용할 수 없다"는 규칙은 **관리·선택에만** 적용되고 **렌더링용 읽기는 공개**여야 합니다. 이미지 접근 방식도 이 점을 전제로 설계해야 합니다.
4. **블록 개수는 사실상 최대 1,200개입니다.** 20×20×3 칸에 칸당 블록 1개라서 "개수 제한 없음"과 충돌하지는 않습니다. 렌더링 성능 걱정은 크지 않습니다.
5. **좋아요순 정렬은 전체 전시 공간의 좋아요 수가 필요합니다.** 파일 기반 저장에서는 목록 조회 성능이 설계 이슈가 되므로 3·4장에서 다룹니다.

## 3. JSON 데이터 구조와 관계

### 설계 원칙

- ID는 불투명한 값(`u_`, `g_`, `a_`, `d_`, `b_` + UUID)을 씁니다. 아이디(한글 포함)를 파일 경로에 쓰면 유니코드 정규화와 대소문자 문제가 생깁니다.
- 모든 JSON 파일 최상단에 `schemaVersion`을 둡니다.
- 시간은 ISO 문자열(UTC)로 저장합니다.
- 이미지는 JSON에 넣지 않고 파일로 저장하며, 경로는 ID 규칙으로 유도합니다. 파일 갱신 시 브라우저 캐시를 피하도록 `rev`(정수)를 올립니다.

### 파일별 스키마

```jsonc
// data/users.json
{ "schemaVersion": 1, "users": [
  { "id": "u_…", "username": "모두", "usernameKey": "모두",   // key = NFC + 소문자 (중복 판정용)
    "passwordHash": "…", "createdAt": "…" } ] }

// data/users/{userId}/artworks.json
{ "artworks": [
  { "id": "a_…", "title": "노을", "titleKey": "노을", "description": "",
    "createdAt": "…", "updatedAt": "…", "rev": 1 } ] }

// data/users/{userId}/designs.json
{ "designs": [
  { "id": "d_…", "name": "벽돌", "nameKey": "벽돌",
    "createdAt": "…", "updatedAt": "…", "rev": 1 } ] }   // 면 이미지는 파일 3개

// data/galleries/{galleryId}/gallery.json
{ "id": "g_…", "ownerId": "u_…", "name": "…", "description": "",
  "cover": null,                    // 또는 "g_….jpg"
  "createdAt": "…",
  "blocks": [
    { "id": "b_…", "x": 3, "y": 7, "z": 0,       // x,y: 0~19 / z: 0~2
      "designId": null,                           // null = 기본 회색
      "frame": null }                             // 또는 { "artworkId": "a_…" | null }
  ] }                                              // artworkId null = 빈 액자

// data/galleries/{galleryId}/likes.json
{ "userIds": ["u_…"] }

// data/galleries/{galleryId}/guestbook.json
{ "entries": [
  { "id": "m_…", "authorId": "u_…", "content": "…",
    "createdAt": "…", "updatedAt": "…" } ] }       // 화면에는 createdAt의 날짜만 표시
```

### 관계

```
User 1 ─ N Artwork        User 1 ─ N BlockDesign        User 1 ─ N Gallery (최대 5)
Gallery 1 ─ N Block (좌표 (x,y,z) 유일, 최대 1,200)
Block N ─ 0..1 BlockDesign   (designId, null = 회색)
Block 1 ─ 0..1 Frame         (블록에 내포)
Frame N ─ 0..1 Artwork       (artworkId, null = 빈 액자)
Gallery 1 ─ N GuestbookEntry (N ─ 1 User)
Gallery N ─ M User           (Like, 쌍 유일)
```

액자는 "블록 앞면당 1개"이고 블록과 생명주기가 같아서 블록 안에 내포했습니다. 작품과의 관계는 `artworkId` 참조로만 두어, 명세의 "작품 원본과 액자 연결을 분리" 요구를 충족합니다.

### 삭제 시 처리 규칙

| 삭제 대상 | 함께 삭제 | 값만 변경 | 유지 |
|---|---|---|---|
| 전시 공간 | 블록, 액자, 방명록, 좋아요, 대표 이미지 파일(제안) | 없음 | 작품, 블록 디자인 |
| 블록 | 그 블록의 액자 | 없음 | 작품 파일, 디자인 |
| 액자 | 없음 | 없음 | 블록, 작품 |
| 작품 | 작품 레코드 + PNG 파일 | 이 작품을 참조하는 액자의 `artworkId` → null | 블록, 액자 |
| 블록 디자인 | 레코드 + 면 이미지 3개 | 이 디자인을 쓰던 블록의 `designId` → null | 블록 위치, 액자 |

- 작품과 디자인은 소유자만 쓸 수 있으므로, 참조를 정리할 범위는 **그 소유자의 전시 공간(최대 5개)** 으로 한정됩니다.
- 서버는 읽을 때도 "끊어진 참조는 회색 블록·빈 액자로 취급"하는 방어 로직을 둡니다. 삭제 중 장애가 나도 화면이 깨지지 않게 하기 위해서입니다.

### 목록·정렬 성능

전시 공간이 폴더별로 흩어져 있어서 좋아요순 목록을 만들려면 전체를 읽어야 합니다. 서버 시작 시 전시 공간 요약(이름, 소유자, 좋아요 수, 생성일)을 **메모리 캐시**로 올리고, 변경 시 파일과 캐시를 함께 갱신하는 방식을 제안합니다. 서버가 단일 프로세스이고 세션도 메모리라는 전제와 맞습니다.

## 4. 서버와 클라이언트의 역할

| 영역 | 서버 | 클라이언트 |
|---|---|---|
| 인증 | 가입 검증, 해시, 세션 발급·파기, `/me` | 오류 문구 표시, 상단 메뉴 전환 |
| 접근 제어 | 페이지·API 가드(페이지는 302, API는 401/403), 소유자 검사 | 401 응답 시 로그인 페이지로 이동하는 공통 처리 |
| 검증 | **모든 규칙의 최종 판정**(길이, 중복, 한도, 좌표 범위, 소유권) | 입력 중 즉시 피드백(글자 수 카운터 등). 보조 수단 |
| 저장 | JSON·이미지 입출력, 원자적 쓰기, 동시성 제어, 연쇄 삭제 | 없음 |
| 이미지 | PNG/JPG 시그니처·크기 검사, 파일 교체·삭제 | 캔버스에서 PNG 생성·업로드 |
| 드로잉 | 없음 | 펜·지우개·채우기·전체 지우기, 편집 중 상태(저장 전에는 서버 반영 없음) |
| 아이소메트릭 | 없음 | 투영·렌더링·키보드 선택 위치 처리, 텍스처 캐시, 미리보기 |
| 편집기 | 각 조작의 유효성(점유 칸, 층 범위, 참조 소유권) 검증 후 반영 | 모드 상태, 확인 창, 선택 중인 디자인·작품 |
| 목록·정렬 | 정렬(좋아요순 동률은 최신순), 페이지 분할 | 정렬 UI, 렌더링 |
| 좋아요 | 중복 방지, 개수 집계 | 버튼 상태 표시 |
| 방명록 | 작성자 권한 검사, 10개 단위 페이징, 마지막 페이지 보정 | 인라인 수정 UI, 글자 수, 페이지 번호 구성, 스크롤 |

### API 윤곽 (경로명은 제안)

| 그룹 | 엔드포인트 |
|---|---|
| 인증 | `POST /api/auth/signup`, `login`, `logout` / `GET /api/auth/me` |
| 내 정보 | `GET /api/me` (아이디, 가입일, 전시 공간 수, 작품 수) |
| 작품 | `GET/POST /api/me/artworks`, `PATCH/DELETE /api/me/artworks/:id`, 이미지 교체 |
| 디자인 | `GET/POST /api/me/designs`, `PATCH/DELETE /api/me/designs/:id` |
| 전시 공간 | `GET /api/galleries?sort=&page=`, `GET /api/users/:username/galleries`, `GET /api/galleries/:id`(렌더링 묶음: 블록, 사용 디자인, 사용 작품, 좋아요 수, 내 좋아요 여부), `POST`, `PATCH`, `PUT cover`, `DELETE` |
| 블록·액자 | 기존 API 구조 조사 후 확정. 예: 블록 설치·수정·삭제 및 액자 설치·제거를 별도 작업으로 처리. 액자 교체는 제거 후 재설치 |
| 좋아요 | `PUT/DELETE …/like` (같은 요청을 반복해도 결과가 같게) |
| 방명록 | `GET …/guestbook?page=`, `POST`, `PATCH /:entryId`, `DELETE /:entryId` |

편집기 API는 갤러리 전체를 통째로 저장하는 방식이 아니라 **조작 단위**로 나눴습니다. 서버가 규칙을 조작마다 검증할 수 있고, 두 탭에서 편집해도 덮어쓰기 사고가 적습니다.

## 5. 구현 순서

| 단계 | 내용 | 완료 확인 기준 |
|---|---|---|
| 0 | 미결정 사항 확정, 골격(Express, 세션, 설정 상수), 파일 저장소(원자적 쓰기, 뮤텍스), ID·문자열 유틸, 오류 응답 형식 | 서버 기동, 저장소 읽기·쓰기 동작 |
| 1 | 인증(가입·로그인·로그아웃·`/me`), 접근 가드, 상단 메뉴, `sign_in`, `main` 뼈대 | 모든 가입·로그인 오류 문구, 리다이렉트 규칙 |

| 3 | 전시 공간 CRUD + 대표 이미지 + `gallery_create` + 마이페이지(전시 공간·작품 관리, 통계) | 5개 한도, 이미지 검증, 삭제 확인 |

| 5 | 블록 디자인 CRUD + `design_edit`(면별 캔버스, 면 매핑, 저장 시 미리보기 갱신) + 편집기에 디자인 선택·변경 + 디자인 삭제 연쇄 | 수정 시 사용 중인 모든 블록 반영, 삭제 시 회색 전환 |
| 6 | 액자 설치·제거, 작품 변경은 기존 액자 제거 후 재설치, 빈 액자, 작품 삭제 연쇄 | 작품 삭제 후 빈 액자 유지, 블록 제거 시 액자 동반 제거 |

| 9 | 전시 공간 삭제 연쇄, 오류 처리 점검, 고아 파일 정리, 반응형, 전체 시나리오 점검 | 명세 체크리스트 전 항목 통과 |
